## Findings supplied for correction

1. **Attribution:** “Powered by Nansen API” could imply that the synthetic deck came from Nansen. The offline UI needed exact wording that distinguishes a build for the API from synthetic data.
2. **Scoring-test strength:** the original suite did not pin all 15 played-round/guess combinations to fixed correct actions, correctness, and points. It could therefore miss mutations that always return Buy, always report correct, or always award one point. Success and every typed error also needed explicit `Cache-Control: no-store` coverage.
3. **Answer independence:** forbidden-key/value scans did not prove that an innocently renamed field could not derive from the answer. Each question needed byte comparison against an otherwise-equivalent compilation with a different answer and different future events.
4. **Deck and transformation boundaries:** the selected-answer mix, rejection of unplayed IDs, every public relative-time/size-band transformation, and runtime-shaped `t0`, `$2,500`, and 48-hour boundaries needed direct assertions.
5. **Client submission behavior:** state-based disabling left a pre-render double-activation window. Successful JSON was trusted through a TypeScript cast, and stale responses could affect a later round or replay. The client needed a synchronous in-flight guard, complete runtime validation, safe retry after malformed success, and request-generation invalidation.
6. **Server-only enforcement:** the private module relied on its path, comments, and a regex test rather than the framework-supported `server-only` marker.
7. **Accessibility:** focusing the `aria-live` reveal risked duplicate announcements. The reveal needed one announcement region, focus on the next actionable control, and removal of the redundant score label.
8. **Public policies:** the current offline release needed concise Terms and Privacy pages, footer navigation, and documentation requiring reconsideration when production collection changes.
