## Blocking findings and dispositions

1. **Discovery pagination was unbounded within the pilot.** The original ten-day, token-wide discovery item could consume all ten pilot calls before sampling other periods or covering candidates. Candidate extraction also waited for terminal pagination.
   - **Disposition:** corrected in adapter/state/schema version 2. Discovery uses three non-overlapping six-hour periods at approximately 36, 26, and 16 days before retrieval, page 1 is spread across all windows, every window is capped at two pages, and total discovery is capped at six upstream calls. Every valid page is processed immediately. Capped work is `sampled`, never complete. With no candidates, useful work ends after six calls; with candidates, their coverage is prioritized after the initial three-window sample.

2. **Discovery evidence was too weak and privacy handling depended on cloning private state.** The review requested useful page density and rejection evidence without exposing provider-private values.
   - **Disposition:** each discovery page now emits an explicit allowlisted aggregate containing row/valid/invalid counts, categorical rejection counts, `$25,000+` row count, distinct candidate-fingerprint count, coarse time-span and latency bands, returned page metadata, and safe reported cost. Report version 2 is constructed field-by-field and omits addresses, hashes, labels, exact values, and exact timestamps.

3. **Coverage was token-wide rather than candidate-specific.** Local wallet filtering could not establish that provider coverage was complete for one candidate, and same-cutoff candidates could collide in work identity.
   - **Disposition:** coverage includes the fixed token plus `filters.trader_address` from validated discovery only. Work IDs are `coverage-${candidateId}`; request/cache identity includes purpose and wallet. A synthetic runner regression preserves two independent candidates sharing one cutoff. The supplied review identifies this field in the endpoint schema, but no live request has verified provider behavior.

4. **Duplicate handling could create false No trade.** Exact rows were collapsed, including across pages, before candidate ambiguity was assessed.
   - **Disposition:** any exact or cross-page duplicate involving the filtered candidate rejects coverage as `duplicate-or-unstable-pagination-row`; conflicting rows also reject. The reproduced two-by-`$1,300` same-transaction case is unscorable. Discovery duplicates may be counted but candidate IDs prevent duplicate work.

5. **Coverage evidence was synthesized from cutoff constants.** It did not prove that the actual requested interval covered both required rules windows.
   - **Disposition:** normalization returns the work item's actual local request bounds, and compilation passes those bounds into rules version 4. One-millisecond-short lookback or answer coverage is rejected in mutation regressions. Provider-inclusive request overlap and local half-open filtering remain in force.

6. **The pilot limit was not sufficiently narrow at the runtime boundary.**
   - **Disposition:** CLI text must match a digits-only integer from 1 through 10; signed, padded, zero-padded, decimal, exponential, zero, and larger inputs reject. The direct runner also rejects numeric values outside 1–10. The 130-attempt/credit ceilings remain global safety caps and cannot be reached in one current run.

7. **Fingerprint and cache identity omitted required compatibility/purpose data.**
   - **Disposition:** fingerprints include adapter, state, and schema versions, purpose, and the complete normalized request, including wallet. Cache/state/schema versions were advanced. Discovery and coverage differ even for otherwise equal fields. Cache-hit tests prove zero fetches, zero new ledger attempts/successes, and zero discovery/coverage call-counter increments.

8. **Direct accounting, report, and malformed-state regressions were incomplete.**
   - **Disposition:** tests now cover direct attempt and retained-credit caps, unknown-charge reservation retention, report allowlist injection, cache counter exclusion, and malformed/truncated private state failing before fetch.

9. **Failure and recovery behavior was vague and used the wrong lock name.**
   - **Disposition:** diagnostics say “Acquisition lock.” Cached validation failures carry categorical `cached-page-*` reasons. The runbook states that crash-left locks, pending/unknown attempts, missing successful caches, malformed state, and settled persistent provider failures stop automatic continuation. Recovery preserves evidence for independent reconciliation and never instructs blind deletion, accounting edits, or automatic replay.

10. **Atomic rename lacked containing-directory durability.**
    - **Disposition:** ledger, state, cache, and manifest/report JSON writes sync the containing directory after rename where supported. Files and directories retain restrictive/no-follow controls. An injected directory-sync failure on the ledger reservation prevents the synthetic fetch.
